# AIに改修を頼む手引き（AI_GUIDE）

**この文書は誰向けか**：ギャラリーの改修を、Claude Code などのAIエージェントに頼みたい人。何を渡し、どんな制約を守らせ、受け取ったあとに何を確かめるかをまとめています。AI自身が読む場合も、ここと [DEVELOPMENT.md](DEVELOPMENT.md) が前提です。

流れは3つ：**渡す → 依頼文を書く → 受け取って確かめる**。

---

## 1. AIに渡すもの

| 渡すもの | 理由 |
| --- | --- |
| [DEVELOPMENT.md](DEVELOPMENT.md) | 3ファイルの役割、画面とサーバーの約束、スプシの列、データ仕様、直す箇所の一覧がある。AIはこれを最初に読む |
| 直したいファイルの**全文**（`Code.gs` / `index.html` / `guide.html` のうち必要なもの） | 断片だけだと、他の部分との整合が取れず壊れやすい。画面を変えるなら `index.html`、仕様を変えるなら `Code.gs` と `guide.html` も |
| 何を変えたいか、なぜか | 次の節の書き方で |

データ仕様は DEVELOPMENT.md の「[データ仕様](DEVELOPMENT.md#データ仕様)」が正なので、別に貼る必要はありません（DEVELOPMENT.md を渡せば入っています）。

Claude Code などでリポジトリを直接開ける場合は、`tools/docs/DEVELOPMENT.md` と `tools/gas/` の場所を伝えれば足ります。チャット形式のAIに頼む場合は、各ファイルの全文を貼り付けてください。

### 「何を変えたいか」の書き方

**画面上の振る舞いで、理由とセットで書きます**（コードの直し方ではなく）。

- 良い：「タグを複数選んで絞り込みたい。今は1つしか選べず、『顕微鏡』かつ『治具』のものを探せないから。」
- 悪い：「`state.tag` を配列にして `filter` を書き換えて」（実装に踏み込みすぎで、AIの判断の余地を奪い、副作用の確認も抜けやすい）

## 2. 依頼文のひな形（コピペして使う）

下の枠を丸ごとコピーし、`【 】` の部分だけ書き換えてください。**「守ってほしい制約」は毎回そのまま貼ります。**

```markdown
あなたは研究室の「3Dプリント作品ギャラリー」（Google Apps Script 製のWebアプリ）の改修を担当します。
添付の DEVELOPMENT.md を最初に読み、構成・データ仕様・「データ仕様を変えるときに直す箇所」を把握してから作業してください。

## 変えたいこと
【画面上の振る舞いで書く。例：タグを複数選んで絞り込みたい。今は1つしか選べない】

## なぜか
【理由。例：『顕微鏡』かつ『治具』の作品を探したいから】

## 対象ファイル
【例：index.html（添付）。仕様に関わるなら Code.gs と guide.html も】

## 守ってほしい制約
- Code.gs / index.html / guide.html の3ファイル構成を変えない（ファイルの追加・分割をしない）
- 外部ライブラリやGASの拡張サービスを追加しない（コピペで動く状態を保つ）
- meta.json の既存キーの意味を変えない。キーを足すなら任意項目にし、古い作品が壊れないようにする
- データ仕様を変える場合は、DEVELOPMENT.md の「データ仕様を変えるときに直す箇所」の一覧をすべて直す
- 変更したファイルは全文で出す（差分の断片ではなく、そのまま貼り替えられる形）

## 最後に出してほしいもの
- 変更点の一覧（ファイルごと、何をなぜ変えたか）
- DEVELOPMENT.md のどこを更新すべきか（更新後の文面案つき）
- 確認してほしい操作の手順（画面のどこを押してどうなれば正しいか）
```

## 3. 依頼文の例

### 良い例

```markdown
（ひな形の続きとして）

## 変えたいこと
一覧の左の絞り込みで、タグを複数選んでも使えるようにしたい。選んだタグを全部持つ作品だけに絞る（AND）。
選んだタグは、一覧上の「効いている絞り込み」に1つずつ出して、×で個別に外せるようにする。

## なぜか
「顕微鏡」で絞ったあと、さらに「治具」で絞りたい。今は1つしか選べず、2つを同時に満たす作品を探せない。

## 対象ファイル
index.html（添付）。データ（meta.json、Code.gs）は変えない。
```

効く理由：振る舞い（AND、表示、解除）と理由が書いてあり、**データ仕様には触らない**と範囲が決まっている。AIは `index.html` だけを直せばよく、制約も守りやすい。

### 悪い例

```markdown
タグ絞り込みを使いやすくして。あと状態に「保管中」も足しといて。
```

困る点：

- 「使いやすく」では、何が正解かAIにも人にも判断できない（複数選択か、検索か、見た目か）。
- 「状態を足す」は**データ仕様の変更**で、`Code.gs` / `index.html` / `guide.html` / `_template` / DEVELOPMENT.md まで直す箇所が広い。2つの依頼が混ざっていて、確認も難しい。
- 対象ファイルや理由が無く、既存の作品（`status` が3つのまま）への影響も考慮されない。

1回の依頼は1つの変更にします。データ仕様の変更は、それ単独で依頼してください。

## 4. 受け取ったあとの確認

AIが出したコードを、いきなり本番に貼らないでください。次の順で確かめます（詳しい手順は DEVELOPMENT.md の「[本番での確認手順](DEVELOPMENT.md#本番での確認手順)」）。

1. **AIの報告を読む**：変更点の一覧と、「DEVELOPMENT.md のどこを更新すべきか」が出ているか。3ファイル構成・外部ライブラリなしの制約が守られているか（ファイルが増えていないか、`<script src=…>` や外部のURLが増えていないか）。
2. **スプシごとコピーしたテスト環境で同期を試す**：本番のスプシを「ファイル → コピーを作成」し、コピー側の GAS に新しいコードを貼る。コピー側の `ITEMS_FOLDER_ID`（プロジェクトの設定 → スクリプト プロパティ）を**テスト用フォルダ**に向けて、メニュー「ギャラリー → 今すぐ同期」を試す。本番の `items/` は触らない。
3. **「デプロイをテスト」のURLで画面を確認する**：エディタの「デプロイ → デプロイをテスト」のURLで、頼んだ変更が動くことと、**今まで動いていた部分が壊れていないこと**（一覧、絞り込み、詳細、要対応、「作品を追加する」パネル、スマホ幅）を見る。
4. **本番を更新する**：本番の GAS に貼り替え、「デプロイ → デプロイを管理」から**新バージョンを出して**既存のデプロイを更新する（URLが変わる「新しいデプロイ」は使わない）。
5. **控えと文書を更新する**：`tools/gas/` の控えを新しいコードに差し替え、AIが示した内容で DEVELOPMENT.md を更新する。データ仕様を変えた場合は、README の説明やギャラリーの「作品を追加する」と食い違っていないかも確認する。

リポジトリで作業している場合は、ローカルのテスト（`cd dev/gas-test && node --test`、`python -m unittest discover -s dev/fusion-test -v`、`node dev/preview/build.mjs`）もAIに実行させ、結果を報告させてください。ただしこれらは本番のGASやDriveの挙動までは確かめません。上の2〜3が必要です。

## AIが迷いやすい点（AIにも読ませたい注意）

- `Code.gs` には `var` の設定値と、`_` で終わる非公開関数がある。画面から呼ぶ関数（`getGalleryData` `syncNow` `resyncItem`）の名前と戻り値は、`index.html` との約束なので変えない。
- `guide.html` にはスクリプトレット（`<?` の構文）を書かない。`index.html` にも、`<?!= include('guide') ?>` 以外は足さない。
- 検査ルールを変えると、指紋が変わって全作品が再読み込みされる（仕様どおり）。列を足したら「全部作り直す」が必要。
- スプシは手で編集しない前提。画面や機能で「スプシを直す」方向に寄せない。正は `items/` の `meta.json`。
